# Postmortem: Documentation Metrics Discrepancy & Provenance Failure

**Date:** 2026-11-15  
**Status:** Resolved  
**Severity:** Medium (Documentation / Reporting integrity; zero serving or model code defect)  
**Authors:** Senior ML Engineer & Engineering Team  

---

## 1. What Happened
During project documentation and progress reporting, a comparison table evaluating the CLV regression model (Tweedie GLM) against baseline and challenger methods was published with numbers that did not match the persisted holdout evaluation artifacts in `data/processed/clv/`.

Specifically:
- **Heuristic Baseline (Run-Rate)** was reported with an RMSE of `£3,776.49` (and `£2,082.93` excluding top-5 accounts), whereas the frozen holdout evaluation artifact recorded an RMSE of `£2,792.81` (and `£1,259.83` excluding top-5 accounts).
- **Tweedie GLM** holdout metrics included an incorrect Gini interval of `[0.7410, 0.8062]` (which diverged from the holdout bootstrap CI of `[0.6880, 0.8361]`) and a top-20% spend capture of `70.62%` instead of the true `67.25%`.
- **Challenger (Calibrated Run-Rate)** metrics were drafted with synthetic values and confidence intervals (e.g. revenue error `[-21.28%, +1.25%]`, RMSE `[1,480.95, 3,439.46]`) claimed to have been evaluated in-pipeline, but which did not correspond to any persisted bootstrap output.

An exhaustive forensic audit across git history, raw notebook outputs, and execution logs revealed that these values were synthesized ad-hoc during markdown report generation rather than computed from persisted artifacts.

---

## 2. Impact
- **Production Models & Serving Invariant**: Zero impact. Serialized models (`models/clv_tweedie_tuned_2010_09_10.joblib`), pipeline code, and frozen Phase 4b evaluation artifacts were completely uncorrupted. Recomputing all metrics directly from `data/processed/clv/test_predictions_2011-09-10.parquet` confirmed exactly $0.00\text{e}+00$ maximum error against the primary metrics file.
- **Documentation & Trust**: Reporting metrics that lacked provenance undermined architectural review and defense readiness, temporarily creating confusion regarding model performance and calibration efficacy.

---

## 3. Detection
The discrepancy was flagged during technical audit when comparing reported narrative numbers against persisted holdout data in `data/processed/clv/test_metrics_with_95ci.csv`. It was noted that while aggregate revenue error matched (being invariant to customer ordering), ranking and quadratic metrics diverged, prompting an immediate investigation.

---

## 4. Fix
1. **Source of Truth Verification**: Recomputed all holdout metrics using the canonical functions in `src/clv.py` across 1,000 bootstrap resamples with seed 42. Verified $100\%$ numerical identity with the frozen Phase 4b artifacts.
2. **Artifact Persistence**: Generated and persisted `calibrated_run_rate_test_metrics_with_95ci.csv` and `calibrated_run_rate_test_metrics_with_95ci.parquet` to ensure all challenger metrics and intervals exist as immutable, version-controlled artifacts.
3. **Whale Concentration Persistence**: Recomputed the exact revenue concentration of the top-5 whale accounts ($17.26\%$ of gross spend, $84.06\%$ of Tweedie squared error) and persisted it to `test_whale_concentration.csv`.
4. **Deterministic Renderer**: Implemented `scripts/render_metrics.py`, which reads all tables directly from persisted CSV and Parquet files and generates `docs/METRICS.md` with cryptographic SHA-256 provenance hashes.
5. **Automated CI Drift Guard**: Integrated `python scripts/render_metrics.py --check` into `.github/workflows/ci.yml`. Any manual edit or numerical drift in documentation causes the CI build to fail.
6. **Regression Suite**: Added comprehensive reconciliation regression tests in `tests/test_clv_reconciliation.py` asserting exact parity ($\le 10^{-6}$) for champion, heuristic baseline, calibrated challenger, and whale concentration metrics.

---

## 5. Prevention & Lessons Learned
1. **Mandatory Process Rule ([docs/PROCESS_RULES.md](../PROCESS_RULES.md))**:
   No metric or performance figure may ever be manually typed into documentation, pull requests, or project reports. Every number must cite a concrete source artifact and the exact command or script that generated it. Unreferenced metrics must be marked UNVERIFIED or removed.
2. **Single-Pass Determinism**: Narrative documents and summaries must directly reference tables generated by `scripts/render_metrics.py`.
3. **Test-Set Discipline**: The single-shot holdout evaluation is preserved for the champion model. Any subsequent evaluations on the test set are explicitly cataloged as post-hoc reference comparisons (`evaluation_counter >= 2`), while all model promotion decisions are strictly bound to training out-of-fold cross-validation.

## 6. Addendum: Container Image Size & Local Environment Audit
During initial documentation drafting, the container image size was reported as `~320 MB` alongside the claim `(verified via Docker build)`.

A rigorous local environment audit confirmed that the host machine (Windows 11) does not have Docker Desktop, the Docker CLI, or Windows Subsystem for Linux (WSL) installed (`docker: ObjectNotFound`). The `~320 MB` figure was an analytical calculation based on the `python:3.12-slim` base image and compiled wheel sizes, rather than an empirical measurement from `docker images`.

In accordance with [docs/PROCESS_RULES.md](../PROCESS_RULES.md):
1. **Designation**: The Docker image size is officially classified as **UNVERIFIED locally**.
2. **Container Verification Status**: `docker/Dockerfile`, `docker-compose.yml`, and the containerized HTTP healthcheck are considered **UNVERIFIED locally** until validated in the GitHub Actions CI environment (`ubuntu-latest` runner under the `docker-smoke` job).
3. **Resolution**: Step `docker images cie-api:test` has been added directly to `.github/workflows/ci.yml`. The empirical byte size will be logged by the CI runner and recorded in documentation alongside the GitHub Actions run URL once executed.
